# Mysport Web 前端开发规范

本文档为本仓库 **唯一** 的前端工程约定。评审代码、编写功能、重构与修 Bug 均以本文为准；若与临时口头约定冲突，以本文为准。

---

## 1. 适用范围与技术栈

- **运行时**：Node.js `>=20.19.0`（见 `package.json` engines）。
- **框架**：Vue 3（Composition API + `<script setup>`）。
- **构建**：Vite 8；包管理以仓库锁文件为准，勿随意降级核心依赖大版本。
- **状态**：Pinia；路由：Vue Router；多语言：`vue-i18n`。
- **样式**：Sass/SCSS；基础样式含 `normalize.css`；移动端适配遵循项目既有 PostCSS（如 `postcss-pxtorem`）配置，**不**自创新的根字号策略除非经评审。

---

## 2. 目录与职责

| 区域 | 职责 |
|------|------|
| `src/components/` | 跨页面复用的展示型组件，保持无业务站点强耦合；若必须依赖站点，通过 props / inject / 配置注入。 |
| `src/views/` | 页面级视图，按路由或业务域分子目录；页面内局部组件可放在 `views/.../components/`。 |
| `src/store/` | Pinia 模块，按领域拆分；避免单文件巨型 store。 |
| `src/router/` | 路由表、守卫、路由元信息（如 `meta.titleKey`）。 |
| `src/i18n/` | 语言包、i18n 初始化；**用户可见文案默认走 i18n**，禁止长期硬编码中英文混用。 |
| `src/config/` | 站点/环境相关配置（如 `siteKey`、主题来源）。 |
| `src/hooks/` | 可复用的组合式函数（`useXxx`）。 |
| `src/api/` 或 `src/services/`（若存在） | 请求封装、与后端契约；错误与 loading 策略在此层或 store 层统一，避免组件内到处 `fetch`。 |

新增目录须有明确边界；不要为了「整洁」过度抽象。

---

## 3. 命名与文件

- **组件文件**：PascalCase，如 `MatchCard.vue`。
- **组合式函数**：`use` 前缀 + camelCase，如 `useTheme.ts`。
- **Store**：`useXxxStore`，文件名与模块名一致、可检索。
- **路由 name / path**：kebab-case 路径与语义化 name；`meta` 中用于标题的键与 i18n key 对齐。
- **CSS 类名**：BEM 或与现有文件保持一致；避免全局污染，优先 scoped；深度选择器仅作最后手段并注释原因。

---

## 4. Vue 组件规范

- **默认**使用 `<script setup>` + Composition API；选项式 API 仅用于兼容遗留代码。
- **Props / Emits**：显式声明类型与默认值；事件名使用 camelCase 或与现有代码一致。
- **单一职责**：单文件组件以「一个主要 UI 职责」为限；超过约 200 行模板或脚本应考虑拆分。
- **副作用**：在 `onMounted` / `watch` 中订阅的监听、定时器、事件，必须在 `onBeforeUnmount` 中成对清理。
- **列表渲染**：`:key` 使用稳定唯一 id，禁止滥用 index（除非静态列表）。
- **与路由解耦**：可复用组件不直接 `useRoute()` 读取参数，由父组件传入或通过 props，降低测试与复用成本。

---

## 5. 状态管理（Pinia）

- 局部 UI 状态优先组件内 `ref` / `computed`；跨页面或持久化需求再用 Pinia。
- Store 中避免存储可从路由或接口直接推导的冗余数据；注意与服务端状态的一致性（刷新、重连）。
- 使用 `storeToRefs` 解构响应式 state，避免直接解构丢失响应式。

---

## 6. 国际化（vue-i18n）

- 所有面向用户的字符串应进入语言包；例外：调试日志、技术型错误码展示（仍建议映射为用户可读文案）。
- 插值与复数规则按 `vue-i18n` 文档处理；站点名、品牌名通过参数传入（见现有 `siteName` 用法）。
- 新增 key 时保持各语言文件键集合一致，缺失语言用英文或占位并跟进补齐。

---

## 7. 样式与主题

- 优先复用设计 token（变量、mixin），与 `useTheme` 等现有机制一致。
- 颜色、间距、字号避免魔法数泛滥；若设计未给 token，在局部注释设计稿或约定来源。
- 图片与图标：优先现有资源管线（Vite 静态资源、`?url` 等）；注意 `alt` 与性能（懒加载、合适格式）。

---

## 8. 性能与体验

- 路由级代码分割：大型页面使用动态 `import()`。
- 避免在渲染路径上创建大对象或重计算；复杂逻辑用 `computed` 或拆子组件。
- 网络：列表分页、防抖节流、取消过时请求（`AbortController`）按场景采用。
- 不引入明显增大包体的依赖而不经讨论；检查 tree-shaking 与按需引入。

---

## 9. 可访问性与 SEO

- 语义化标签：`button` / `a` / 标题层级合理；交互元素具备可聚焦与键盘可操作（在业务允许范围内）。
- `document.title`、`html[lang]` 与路由、语言切换保持同步（沿用现有 `App.vue` 模式）。
- `meta` 与分享信息若产品需要，在路由或配置层扩展，避免各页复制粘贴。

---

## 10. TypeScript 与类型（若逐步启用）

- 新文件优先 `.ts` / 带类型的 `<script setup lang="ts">`；与既有 `.js` 共存时保持边界清晰。
- 对外 API（组件 props、公共 hook）必须有稳定类型或 JSDoc。
- 禁止使用 `any` 掩盖问题；确需时使用 `unknown` 并收窄。

---

## 11. 错误与用户反馈

- 用户可见错误信息：友好、可操作（重试、联系支持）；技术细节进控制台或监控系统，不堆叠给用户。
- Loading / 空状态 / 错误态三态齐全，避免白屏与无限转圈。

---

## 12. Git 与协作

- 提交信息使用清晰中文或英文完整句，说明「做了什么、为什么」，关联需求或缺陷编号如有则写上。
- 单次提交聚焦单一主题，便于 bisect 与 review。
- PR 描述包含：背景、方案要点、自测范围、风险与回滚方式。

---

## 13. AI 辅助开发时的约定

- **语言**：与协作者沟通时（含对话回复、思考过程说明、实现解释）使用 **简体中文**，与团队习惯一致。
- 变更应 **最小化**：只改完成任务所需的文件与行，禁止顺带大规模格式化无关文件。
- 引入新依赖、新目录结构、新全局单例前，在 PR 或说明中解释必要性。
- **以本文件与 `.cursor/rules` 中的规则为准**；若模型建议与规范冲突，应调整实现以符合规范。

---

## 14. 修订

规范随项目演进更新；修改本文时应在团队内同步，并在 PR 中简述变更原因。
